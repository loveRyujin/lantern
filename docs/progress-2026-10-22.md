## 本轮优先项：#38 验收对照

背景风险已由 #38 记录：物化 CTE、子查询、GROUP BY、UNION、IN 列表等中间值能令原进程占用约 1.2–2.75 GB；最终结果的行数、列数和字节限制不能代替查询过程的内存上限。

本轮已在本地实现 Linux SQL worker、系统限制、结果编码及回归测试，当前状态为 **已通过本地全量校验，待远端 CI 与审查**。产品侧已核对 `core/sqlx/process_linux_test.go`、`core/sqlx/process_integration_test.go` 和技术设计 §6；开发侧专项采样记录六类 B6 的 RSS 约 306–312 MB、VmPeak 不超过 1 GiB，整数精度、JSON/UTF-8 和超时专项已通过。专项与全量检查的具体结果见文末，不据此宣告远端合并。

1. **进程边界：已实现，有生产入口测试。** `NewTool` 在 Linux 启动自身 worker，测试给父进程 Queryer 配置“一旦被调用即失败”的断言。父进程不执行模型 SQL，完整文件哈希也在 worker 内流式计算。
2. **系统内存上限：已实现并有峰值断言。** shim 在第二次 exec 前设置 `RLIMIT_AS` 软/硬上限为 **1 GiB（1,073,741,824 字节）**，覆盖 Go 运行时和 SQLite 的整个虚拟地址空间。`GOMEMLIMIT=64MiB` 只是辅助；1 GiB 不能解释为 SQLite 堆或 RSS 可用预算。
3. **资源错误：本地集成通过。** NOMEM 或限额确认后的明确 runtime OOM 返回 `sql_result_too_large`；崩溃、协议损坏和启动失败分别分类。Agent 已有相同错误码不增加也不清零连续失败的回归。新增真实工作区并发测试在 worker 产生内存压力期间写审计、创建和批准确认单，再核对持久化结果及下一次正常查询；该并发测试已在本地全量测试中通过。
4. **真实 B6 回归：六类专项与全量检查均通过。** 物化 CTE、子查询、GROUP BY、UNION、IN 列表、ORDER BY random() 各使用独立 worker，断言错误码、空结果、限额确认、峰值和进程回收，另断言 RSS 确实达到中间值压力；不再用 skip 或非零退出码代替这些场景。
5. **生命周期：已实现并有专项。** context 到期杀进程组并 Wait；测试检查 `/proc/PID` 消失、kill 探测返回 ESRCH、下一次正常查询可继续。错误分类测试覆盖普通退出、SIGSEGV、外部 SIGKILL、协议损坏及 OOM 诊断，避免混为一类。
6. **只读与隔离回归：原限制保留，新增文件身份测试。** worker 继续调用只读连接和白名单路径，查询前后核对文件哈希、设备号/inode。新增 symlink、hardlink、rename 替换测试要求返回 `data_busy` 且无泄露；现有写语句、ATTACH、哈希及敏感库回归已在本地全量检查中通过。
7. **记录实际限制：已更新技术设计 §6。** 已写明 Linux 1 GiB 地址空间上限、NOMEM 行为、错误分类、结果预算和低层 `Query` 的边界。**macOS SQL worker 尚未实现，当前返回 `sql_worker_unavailable`，安排在 W4，不能回退父进程执行**；不能将本轮 Linux 改动宣告为跨平台修复。

[#38 的 S5 评论](https://github.com/loveRyujin/lantern/issues/38#issuecomment-6320598096) 要求父进程解析结构化结果，包括峰值和错误码；S8 要求启用真实 B6 回归。若 RLIMIT_AS 令分配返回错误而不是内核直接杀死，应明确说明实际行为，并确认查询及时退出、错误分类准确、峰值满足限制，不能把所有异常退出统称 OOM。

两项评论原为**非阻塞跟进**，本轮一并实现：S1 的非法 UTF-8 TEXT 以带 `encoding` 标识的 base64 对象无损表示；S7 关闭 HTML 转义，并按完整最终 JSON（含列名、元数据、转义和 base64）计入 1 MiB。专项覆盖合法文本、控制字符、Unicode 分隔符、非法 UTF-8、BLOB、后续超大行清空结果及多行累计截断；已随本地全量检查通过，不自动提升为 #38 原始阻塞项。

本地测试、build/vet、并发写入与文件替换回归的结果已汇总于文末。当前可形成 #38 的可 review 交付，远端 CI 与审查待完成，本记录不关闭 Issue、不宣告合并。低层 `Query` 仍是受信任调用方的进程内读取器，不具备中间值总内存硬限制。

新增 `TestSQLWorkerPostQueryIntegrity` 直接调用 `NewTool`，等待真实 worker 持有分析库 fd，并观察三次 CPU tick 增长后再改变文件：

- 原 inode 追加字节：内容变、身份不变，要求可重试 `data_busy`、结果为空。
- 字节完全相同的新 inode 替换：内容不变、身份变，要求同样失败关闭。
